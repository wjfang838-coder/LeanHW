<!-- original-requirements:start -->
Design the System Verilog module `caesar_cipher` to implement a Caesar cipher for character encryption. The module should take an 8-bit ASCII character as input and produce a new character based on a 4-bit key value. The module should handle both uppercase (A-Z) and lowercase (a-z) letters while leaving non-alphabetic characters unchanged.

### Interface

#### Inputs:

- **input_char ([7:0], 8-bit)**: The ASCII character to be shifted. It should be within the range of standard ASCII values.
- **key ([3:0], 4-bit)**: The shift key. A 4-bit value (0-15) determines the shift applied to alphabetic characters.

#### Output:

- **output_char ([7:0], 8-bit)**: The resulting ASCII character after applying the Caesar cipher shift, respecting character casing. Non-alphabetic characters remain unchanged.

## Design Specification:

- **Uppercase Letters**: If the input is an uppercase letter ('A'-'Z'), the character should be modified within the uppercase range.
- **Lowercase Letters**: If the input is a lowercase letter ('a'-'z'), the character should be modified within the lowercase range.
- **Non-alphabetic Characters**: Characters that are not within 'A'-'Z' or 'a'-'z' should remain unchanged in the output.
- **Modulo Operation**: The shifting must wrap around within the alphabet using modulo 26, ensuring characters like 'Z' roll back to 'A' and 'z' to 'a' when shifted.
- Design should follow combinational logic

### Simplified Algorithm:

1. **Check** if `input_char` is an uppercase letter (A-Z):
   - Shift the character by `key` positions within the range A-Z.
2. **Check** if `input_char` is a lowercase letter (a-z):
   - Shift the character by `key` positions within the range a-z.
3. **If not alphabetic**, leave `input_char` unchanged.

### Example Computations:

#### Example 1:

Assume `input_char` = 'h' (`01101000`) and `key` = 3 (`0011`).

1. **Lowercase Handling**:
   - Calculate the shifted position: ((`h` - 'a' + 3) % 26) + 'a'
   - Result: `k` (`01101011`).
2. **Final Output**:
   - The final shifted character for `input_char` 'h' with `key` 3 is 'k'.
   
#### Example 2:

Assume `input_char` = 'y' (`01111001`) and `key` = 8 (`1000`).

1. **Lowercase Handling**:
   - Calculate the shifted position: ((`y` - 'a' + 8) % 26) + 'a'
   - Result: `g` (`01100111`).
2. **Final Output**:
   - The final shifted character for `input_char` 'y' with `key` 8 is 'g'.

1. Module and ports.

The module name is exactly caesar_cipher. It has no public parameters established by the requirements.

The interface artifact lists the ports in this declaration order:

1. input input_char[7:0]
2. input key[3:0]
3. output output_char[7:0]

The spellings, directions, and widths above are normative. The positional declaration order is not established by the authorized sources and is therefore not normative. The module must be instantiated using named connections to input_char, key, and output_char.

3. Reset.

There is no reset port and no reset behavior. The module has no stored state. Therefore reset assertion, reset release, reset values, and a first step after release do not apply.

Implementation choice C1 — initial and pre-observation combinational output: whenever the public input ports have current 8-bit and 4-bit values, including before the first harness observation, output_char is the combinational Caesar-cipher result specified below for that current pair. This is a compatible completion of the source's unstated pre-observation value, not a source-derived hardware power-up guarantee and not a reset-before-use restriction. It introduces no retained initialization state and does not authorize X or Z.

4. Timing.

output_char is combinational, with no clock-cycle latency, capture edge, completion pulse, transaction state, or hold/clear interval. A change to input_char, key, or both selects the result for the resulting current pair independently of prior values. Key zero produces zero shift. Repeated changes and changes that would interrupt a prior settling interval do not create or cancel transactions; only the current pair determines the settled output.

The verification harness permits 1 ns for combinational settling after each input assignment and then samples output_char. The harness samples output_char 1 ns after each input assignment, and at every such observation output_char is the Caesar-shift result of the then-current input_char and key, including the first and every repeated character.

The evaluated full-cycle table is an observation sequence, not a circuit clock: successive rows correspond to successive harness stimuli after their 1 ns settling intervals. The design has no actual clock period or edge. Thus the general autonomous-design convention that row k denotes k times step_ns after settling does not create a clock for this module.

5. Behaviour.

For every current 8-bit input_char value, the current value selects the character class independently: 8'h41 through 8'h5A are shifted within uppercase ASCII, 8'h61 through 8'h7A are shifted within lowercase ASCII, and every other value is passed through unchanged.

For the current 4-bit key, an uppercase or lowercase input character is advanced by key positions with wraparound modulo 26, while a non-alphabetic input is unaffected.

More precisely, interpret input_char and key as unsigned values of their declared widths:

- If 8'h41 <= input_char <= 8'h5A, output_char is 8'h41 + ((input_char - 8'h41 + key) modulo 26).
- If 8'h61 <= input_char <= 8'h7A, output_char is 8'h61 + ((input_char - 8'h61 + key) modulo 26).
- Otherwise, output_char equals input_char exactly.

The addition inside each modulo expression is evaluated on the complete nonnegative character offset and unsigned 4-bit key. The modulo-26 reduction precedes addition of the ASCII base; the final result is represented on the 8-bit output. There is no inactive input level or transaction mode. Simultaneous input_char and key changes use the resulting current pair, and every repeated or interrupted change is evaluated independently.
