<!-- original-requirements:start -->
Design a SystemVerilog `apb_controller` module for handling event-based write transactions with an Advanced Peripheral Bus (APB) interface. The module should control APB signals for write operations triggered by external input signals along with a unique address and a data input, ensuring adherence to the APB protocol. Additionally, the design should include a timeout mechanism to prevent indefinite stalling if the peripheral does not respond within a specified period. This design should only support write operations and not read transactions.

### APB Protocol Overview

The Advanced Peripheral Bus (APB) is a simple, low-latency bus protocol often used to connect peripheral devices in a system. APB operates with a structured two-phase transaction sequence, consisting of a **SETUP** phase and an **ACCESS** phase. This controller is designed to support **write transactions only**, ensuring a straightforward approach to interfacing with peripherals on the APB.

### Design Requirements

- Event-Based Transactions:
    - The controller must handle three independent events: A, B, and C.
    - Each event includes a 32-bit address and 32-bit data for APB write transactions.
   -  Events are triggered by respective select_*_i signals (`select_a_i`, `select_b_i`, `select_c_i`).

#### Transaction Flow and Timing

The transactions follow a three-state flow:
1. **IDLE State**:
     - When any event select signal is asserted, the controller captures the corresponding address and data into internal signals.
     - If multiple select signals are asserted simultaneously, the controller prioritizes them as `select_a_i` (highest priority), followed by `select_b_i`, and then `select_c_i` (lowest priority).
     - The `IDLE` phase lasts for one clock cycle.
     - The default state is **IDLE** state, which it enters after a reset and remains in when no transactions are active   

2. **SETUP Phase**:
   - After the `IDLE` phase, the controller transitions to the `SETUP` phase.
   - in the `SETUP` phase the controller asserts `apb_psel_o`, and `apb_pwrite_o` and set up `apb_paddr_o` and `apb_pwdata_o` with the selected address and data.
   - In this phase, `apb_penable_o` remains deasserted.
   - The `SETUP` phase lasts for one clock cycle.

3. **ACCESS Phase**:
   - After the `SETUP` phase, the controller transitions to the `ACCESS` phase.
   - In `ACCESS`, `apb_penable_o` is asserted high to signal that the data transfer is in progress.
   - The controller remains in this phase, waiting for `apb_pready_i` from the peripheral to be asserted high.
   - In `ACCESS` phase, the signals `apb_psel_o`, `apb_pwrite_o`, `apb_paddr_o`, and `apb_pwdata_o` must remain stable.
   - **Write Transfer with Wait**: If `apb_pready_i` is delayed, the controller stays in `ACCESS` until `apb_pready_i` goes high.
   - **Write Transfer without Wait**: If  `apb_pready_i` goes high in the same clock cycle that the controller enters the `ACCESS` phase, the controller completes the transaction within the same cycle.

   - **Timeout Mechanism**:
      - While in the `ACCESS` phase, a 4-bit timeout counter increments each clock cycle if `apb_pready_i` remains low.
      - If `apb_pready_i` is not asserted within 15 cycles after entering `ACCESS` state, the timeout counter resets the controller to the `IDLE` state and sets all outputs to 0 at the next positive edge, effectively aborting the transaction and preventing indefinite stalling.
      - The timeout counter resets to zero after a successful transaction or when the controller returns to the `IDLE` state.

   - **Return to IDLE**:
      - After a successful transaction (when `apb_pready_i` is asserted), the controller returns to the `IDLE` state, with both `apb_psel_o` and `apb_penable_o` getting deasserted.
      - A new transaction can only start when a select signal (`select_a_i`, `select_b_i`, or `select_c_i`) is asserted and both `apb_psel_o` and `apb_penable_o` are low, ensuring only one transaction occurs at a time.

#### **Total Latency for the Transaction**
- **Minimum Latency**: From the triggering of an event, the minimum number of clock cycles required to complete a transaction and return to `IDLE` without wait states (`apb_pready_i` is asserted immediately) is **3 cycles**:
  - **SETUP State**: 1 cycle.
  - **ACCESS State**: 1 cycle.
  - **Transition to IDLE**: 1 cycle to de-assert signals and return to `IDLE`.
- **Additional Latency**: If `apb_pready_i` is delayed, additional cycles are spent in the `ACCESS` state until the peripheral is ready or a timeout occurs.

#### Inputs:
- **`clk`**: Clock signal, active on the rising edge.
- **`reset_n`**: Active-low asynchronous reset signal that resets the controller to the `IDLE` state, clears the timeout counter, and sets all registers and outputs to 0.
- **`select_a_i`**: Active-high control signal to initiate a transaction for Event A.
- **`select_b_i`**: Active-high control signal to initiate a transaction for Event B.
- **`select_c_i`**: Active-high control signal to initiate a transaction for Event C.
- **`addr_a_i [31:0]`**: Address input for Event A.
- **`data_a_i [31:0]`**: Data input for Event A.
- **`addr_b_i [31:0]`**: Address input for Event B.
- **`data_b_i [31:0]`**: Data input for Event B.
- **`addr_c_i [31:0]`**: Address input for Event C.
- **`data_c_i [31:0]`**: Data input for Event C.
- **`apb_pready_i`**:  Ready signal from the peripheral, active high. It indicates when the peripheral is ready to complete the transaction. The controller checks this signal in the `ACCESS` phase to determine transaction completion.

#### Outputs:
- **`apb_psel_o`**: An active-high signal, asserted during `SETUP`, to select the peripheral for an APB transaction.
- **`apb_penable_o`**: An active-high signal, asserted during the `ACCESS` phase, indicating the transaction is in progress.
- **`apb_pwrite_o`**: An active-high signal indicating a write operation, asserted during the `SETUP` and maintained in the `ACCESS` phase.
- **`apb_paddr_o [31:0]`**: 32-bit address output for the transaction, determined by the selected event's address input (`addr_a_i`, `addr_b_i`, or `addr_c_i`). Defaults to 0 in the `IDLE` state.
- **`apb_pwdata_o [31:0]`**: 32-bit data output for the write operation, based on the selected event's data input (`data_a_i`, `data_b_i`, or `data_c_i`). Defaults to 0 in the `IDLE` state.

### Constraints:
- Assume that event signals `select_a_i`, `select_b_i`, and `select_c_i` are pulse signals high for one clock cycle and are synchronous to the clock. 
- Assume that input data and addresses will be stable inputs when the events are triggered.
- If multiple events are triggered simultaneously, only the highest-priority event will be processed, and the rest will be discarded.
- Assume that a new event will be triggered only when the controller is in an `IDLE` state after the de-assertion of both `apb_psel_o` and `apb_penable_o` for the previous transaction.

3. Reset.

reset_n is active low and asynchronous. Whenever reset_n is low, without waiting for a clk edge, the controller is in IDLE, the 4-bit timeout count is zero, captured address and data are zero, and apb_psel_o, apb_penable_o, apb_pwrite_o, apb_paddr_o, and apb_pwdata_o are all zero. Reset assertion dominates selection, readiness, completion, and timeout. After reset_n returns high, release alone changes nothing: the reset-established IDLE state and zero outputs persist until a later rising edge accepts an event.

Before the first reset assertion, the source does not establish hardware state or output values. That absence does not require X, forbid initialization, or impose a reset-before-use restriction; normal rising-edge operation remains governed by the behavioral laws below.

Implementation choice C1: only the finite executable verification instance starts in the state reached by the documented asynchronous reset: IDLE, timeout zero, captured address and data zero, and all five outputs zero. Its cycle-0 pre-reset observation is therefore concrete. This is a compatible model initialization choice, not a source-derived hardware power-up guarantee, and it changes no reset or subsequent functional law.

4. Timing.

Ordinary state changes occur on rising edges of clk. The five APB outputs are registered state observations; asynchronous reset assertion is the exception and immediately forces every output to zero. apb_psel_o and apb_pwrite_o are high for the one complete SETUP interval and every ACCESS interval. apb_penable_o is low in IDLE and SETUP and high throughout ACCESS. apb_paddr_o and apb_pwdata_o are captured at acceptance, first visible during the following SETUP interval, and stable throughout SETUP and ACCESS. There is no pulse output or periodic output.

For each transaction, E0 is the rising edge that accepts a select pulse while IDLE. The select levels and corresponding 32-bit address and data immediately before E0 determine the registered outputs after E0; the interval after E0 is SETUP and is completed subsequent interval 1. E1 is the next rising edge: it advances the state to ACCESS without changing the captured operands; the interval after E1 is ACCESS cycle 1 and completed subsequent interval 2. apb_pready_i is sampled at the edge ending an ACCESS interval. If it is high during ACCESS cycle 1, E2 completes the write and the interval after E2 is IDLE with all outputs zero, completed subsequent interval 3 from E0.

For timeout timing, ACCESS cycle 1 is the first interval with apb_psel_o and apb_penable_o both asserted. At the ending edge of each of the first fifteen ACCESS intervals, low apb_pready_i increments the 4-bit timeout count. The edge ending ACCESS cycle 15 advances the pre-edge count 14 to post-edge count 15 and retains ACCESS outputs during the following interval. Because readiness was not asserted within those fifteen cycles, the next positive edge is the source-stated timeout action edge: it returns to IDLE, clears the timeout count and captured operands, and makes all outputs zero in the following interval. If readiness is first high during ACCESS cycle 15, its ending edge completes the transfer because readiness was asserted within the deadline. If readiness is first high only in the later count-15 interval, the already-due timeout action occurs. Reset remains dominant.

After successful completion, timeout, or reset, the interval following the deciding edge has all five outputs zero. The timeout count is zero in IDLE and after success, timeout, or reset.

Trace observation convention: the Lean verification object uses full-cycle rows. Row k denotes k * timing.step_ns after settling and observes outputs before that row's active edge; the step then forms row k+1. iface.json supplies no numeric timing.step_ns or timing.sample_offset_ns, so no implicit 10 ns tick or numeric offset is introduced. This observation convention is separate from the circuit's rising-edge, phase-duration, and timeout laws.

5. Behaviour.

The controller supports APB writes only and has no read-transaction function. In ordinary IDLE all five outputs are zero, and apb_pready_i has no effect. A transaction is accepted only at a rising edge while IDLE. Under the source environment constraints, every select is a synchronous one-cycle pulse, its address and data are stable when triggered, and a new event is presented only after the prior transaction has returned to IDLE with apb_psel_o and apb_penable_o low.

At E0, select_a_i has highest priority, select_b_i next priority, and select_c_i lowest priority. If select_a_i is high, addr_a_i and data_a_i are captured and all simultaneous lower-priority events are discarded. Otherwise, if select_b_i is high, addr_b_i and data_b_i are captured and a simultaneous C event is discarded. Otherwise, if select_c_i is high, addr_c_i and data_c_i are captured. If every select is low, IDLE and its zero outputs are retained. The complete 32-bit operand values are used.

In SETUP, apb_psel_o=1, apb_penable_o=0, apb_pwrite_o=1, apb_paddr_o is the accepted address, and apb_pwdata_o is the accepted data. At E1 only the phase advances; throughout ACCESS apb_psel_o=1, apb_penable_o=1, apb_pwrite_o=1, and the accepted address and data remain unchanged. Low apb_pready_i retains ACCESS until the timeout action is due; high apb_pready_i before that action completes at the ending rising edge. Completion or timeout clears every output for the following IDLE interval. In ordinary idle after reset, completion, or timeout, apb_pwrite_o is deasserted.

Implementation choice C2: select_a_i, select_b_i, and select_c_i sampled during SETUP or ACCESS are ignored and are not queued; they do not alter the accepted operands or active transfer. This compatible implementation completion applies only outside the source's legal event environment, because the source requires new events to occur only in IDLE after both apb_psel_o and apb_penable_o are low. The primary write function, priority, phase timing, completion, timeout, and full legal input domain are already established; C2 adds no environmental restriction and resolves no contradictory source law. A later event presented legally in IDLE is accepted normally.

Amendment Q25. The exact original clauses are “The `IDLE` phase lasts for one clock cycle.” and “After the `IDLE` phase, the controller transitions to the `SETUP` phase.” The amendment is limited to a sole synchronous one-cycle select pulse sampled in IDLE, with no competing select pulse and apb_pready_i high in the first ACCESS cycle, and only supersedes any reading that inserts an additional complete IDLE interval after capture.
