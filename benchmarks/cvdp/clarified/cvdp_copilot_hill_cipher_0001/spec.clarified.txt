<!-- original-requirements:start -->
Design an RTL module that implements the Hill cipher encryption algorithm with the following specifications:

- **Block Size**: 3 letters (each letter represented by 5 bits).
- **Key Matrix**: 3x3 matrix (each element represented by 5 bits).
- **Modular Arithmetic**: All operations are based on modulo 26.

The Hill cipher is a classical symmetric encryption algorithm based on linear algebra. It operates on blocks of plaintext and uses matrix multiplication to produce ciphertext.

### 1.1. Basic Concepts

- **Plaintext**: The original message to be encrypted.
- **Ciphertext**: The encrypted message.
- **Block Size**: The number of letters processed at a time. The design has to use a block size of **3**.
- **Key Matrix**: A square matrix used for encryption. For a block size of 3, the key matrix is a 3x3 matrix.
- **Modular Arithmetic**: All calculations are performed on modulo 26, corresponding to the 26 letters of the English alphabet.

### 1.2. Encryption Process

1. **Convert Letters to Numbers**: Map each letter to a number (e.g., A=0, B=1, ..., Z=25).
2. **Form Plaintext Vector**: Group the plaintext into blocks of 3 letters and represent them as column vectors.
3. **Matrix Multiplication**: Multiply the key matrix by the plaintext vector.
4. **Modulo Operation**: Apply modulo 26 to each element of the resulting vector.
5. **Convert Numbers to Letters**: Map the resulting numbers back to letters to obtain the ciphertext.

---

## 2. Module Specifications

### 2.1. Port Definitions

#### 1. Clock and Reset

- **`clk`**: Clock signal for synchronous operation. 
- **`reset`**: Asynchronous reset signal to initialize the module. Set the output `ciphertext` to 0 when the `reset` is HIGH.

#### 2. Control Signals

- **`start`**: A logic HIGH in this input initiates the encryption process.

#### 3. Data Inputs

- **`plaintext`**: 15-bit input representing 3 plaintext letters.
  - Each letter is represented by 5 bits.
  - Bit mapping:
    - `plaintext[14:10]`: First letter.
    -  `plaintext[9:5]`: Second letter.
    - `plaintext[4:0]`: Third letter.

- **`key`**: 45-bit input representing the 3x3 key matrix.
  - Each element is represented by 5 bits.
  - key value should vary from 00000 to 11001.
  - Element mapping:
    - `key[44:40]`: K <sub>00</sub>
    - `key[39:35]`:  K <sub>01</sub>
    - `key[34:30]`:  K <sub>02</sub>
    - `key[29:25]`:  K <sub>10</sub>
    - `key[24:20]`:  K <sub>11</sub>
    - `key[19:15]`:  K <sub>12</sub>
    - `key[14:10]`:  K <sub>20</sub>
    - `key[9:5]`: K <sub>21</sub>
    - `key[4:0]`:  K <sub>22</sub>

#### 4. Data Output

- **`ciphertext`**: 15-bit output representing the encrypted 3 letters.
  - Bit mapping follows the same pattern as `plaintext`.
- **`done`**: A HIGH in this output signal indicates that the encryption process is complete.

### 2.2. Functional Requirements

- **Finite State Machine (FSM)**: Implement an FSM to manage the encryption process.
- **Matrix Multiplication**: Compute the ciphertext vector \( C \) as:

 C<sub>i</sub> = $$\left( \sum_{j=0}^2 K_{ij} \right) \times \left( P_j \right)$$ mod26
  Where:

  - C<sub>i</sub> : i<sup>th</sup> element of the ciphertext vector.
  - K<sub>ij</sub>: Element of the key matrix at row \( i \), column \( j \).
  - P<sub>j</sub>:  j<sup>th</sup> element of the plaintext vector.

- **Modular Arithmetic**: Implement the modulo 26 operation.
- **Synchronous Operation**: All operations should be synchronized with the rising edge of the clock (`clk`).
- **Latency**: The design will have a latency of three clock cycles to produce the ciphertext after applying logic HIGH to `start`

## 3.  **Example**

#### **Input**

-  **Plaintext Block**: `"CAT"` → `[2, 0, 19]^T`
  - Binary Representation:
    - C = `00010`, A = `00000`, T = `10011`
    - **Combined 15-bit input**: `00010_00000_10011`
- **Key Matrix**:

```math
\begin{bmatrix}3 & 10 & 20 \\ 1 & 9 & 15 \\ 8 & 7 & 17 \end{bmatrix}
```

#### **Encryption Process**

**Ciphertext = (Key Matrix × Plaintext Vector) mod 26**

1. Perform the matrix multiplication:

C₀ = (3 * 2 + 10 * 0 + 20 * 19) mod 26  
   = (6 + 0 + 380) mod 26  
   = 22  

C₁ = (1 * 2 + 9 * 0 + 15 * 19) mod 26  
   = (2 + 0 + 285) mod 26  
   = 1  

C₂ = (8 * 2 + 7 * 0 + 17 * 19) mod 26  
   = (16 + 0 + 323) mod 26  
   = 1  

2. **Ciphertext Vector**:

```math
\begin{bmatrix}22 \\ 1 \\ 1\end{bmatrix}
```

3. **Mapping Numbers to Letters**:
   - 22 → U  
   - 1 → B  
   - 1 → B  

   **Ciphertext Block**: `"UBB"`

#### **Output**

- **Ciphertext**: `"UBB"`
- **Binary Representation**:
  - U = `10110`, B = `00001`, B = `00001`
  - **Combined 15-bit output**: `10110_00001_00001`

Explicit local Hill benchmark revision v1. The original prose is retained, with these scoped corrections and added designer decisions.
HB1 (math and example): C_i = (K_i0*P_0 + K_i1*P_1 + K_i2*P_2) modulo 26, using an unsigned sum wide enough for all three products. No modulo 64 truncation is permitted. This corrects the malformed sum formula. In the CAT example, numeric [22,1,1] and its binary encoding remain unchanged; 22 is W, not U, so every UBB label and the U=10110 label are corrected to WBB and W=10110.
HB2 (encoding domain): Alphabet characters use 0..25 as above. For total behavior of the physical 5-bit fields, this local revision additionally defines encodings 26..31 as unsigned numeric operands in the same modulo-26 dot product; the earlier key-domain restriction is superseded only for these encodings. No matrix invertibility condition is needed for encryption.
HB3 (request, latency, retention): At a rising edge E0 with reset low, start high and the engine idle, capture all plaintext and key fields. Busy requests are ignored, with no queue or restart. Subsequent external operand changes do not affect the captured job. After E1 and E2 the old ciphertext is retained and done is 0; immediately after E3 publish the completed ciphertext and done=1. E3 completes the busy interval; a new job can be accepted at E4. done clears at the next rising edge, including a new acceptance, so its completion assertion lasts one interval. Ciphertext holds until the next completion or reset. Level-high start is sampled on each eligible idle edge; it is not edge-detected. No acceptance occurs on the busy E3 completion edge.
HB4 (reset): Asynchronous active-high reset clears ciphertext and done, abandons a pending job and returns the engine to idle immediately. Reset dominates start, remains effective while held high, and no completion can escape an aborted job. No initialization before the first reset is promised. Between rising edges, outputs hold except for asynchronous reset assertion.

Event convention: row k drives input i[k], waits for combinational settling and observes out(s[k], i[k]) BEFORE the active clock edge specified by the behavioral rules below. Use those rules for clock polarity and reset sensitivity. That edge produces s[k+1] = step(s[k], i[k]). A register assigned input i[k] at that edge is visible in row k+1; this is ONE register, not an input register plus an output register. If the behavioral rules specify an asynchronous reset, its assertion takes effect without waiting for that edge; a synchronous reset acts only on its stated edge. Describe transaction latency from the accepting edge, and distinguish the completion pulse from the interval during which result data remains valid.

1. Module and ports


3. Reset
reset is asynchronous and active high. Assertion immediately clears ciphertext and done to zero, abandons any pending job, and returns the engine to idle, regardless of start, operand values, clock level, or a simultaneous rising clock edge. While reset remains high, outputs remain zero and no request is accepted. Release alone leaves outputs zero and the engine idle; it does not accept or advance a job. The first rising clock edge after release accepts a job if start is high, otherwise remains idle with zero outputs. For a first accepted post-reset job, outputs remain zero after acceptance and the next two rising edges; the third subsequent rising edge publishes the result and sets done to one.

Before any reset, ciphertext is hardware unknown until a completed encryption assigns it or reset is asserted; acceptance does not clear it. Before any reset, done is hardware unknown initially, but each reset-low rising edge clears it unless that edge completes an accepted job, when it becomes one. These hardware unknowns are explicitly required by the certain Q1 and Q2 laws, rather than inferred from absence of initialization. No reset-before-use restriction is imposed.

Implementation choice C1: Before the first reset, the control state is idle with zero elapsed busy intervals and no valid captured operands. This compatible initialization decision permits the documented idle acceptance rule to operate before reset; it promises no initialized output. Captured operands have no defined reset data value and are invalid after reset; a fresh acceptance replaces all of them before any computation. Reset establishes idle control state and zero elapsed intervals, invalidates captured operands, and establishes both output values as zero. The operand-invalid state does not affect a result because every accepted job captures all fields.

4. Timing
clk advances operation only on rising edges; falling edges and steady levels do not advance state or change outputs. ciphertext and done are registered outputs, with the asynchronous reset override described above. Anchor E0 to acceptance with reset low, start high, and pre-edge idle state. Immediately after E0, E1 and E2, ciphertext retains its previous value and done is zero. E1, E2 and E3 complete respectively one, two and three intervals after E0. Immediately after E3, ciphertext publishes the captured job's result and done becomes one; E3 does not accept a job. E4 clears done and may accept another job, whose result appears immediately after E7. done lasts one rising-edge interval unless reset truncates it. No periodic output is specified. Ciphertext remains unchanged indefinitely until another completion or reset.

The post-E3 published ciphertext is computed from the operands captured at E0 and the pre-E3 busy state, not the external operands at E3. The elapsed-interval state advances on E1 and E2 and returns to idle on E3 simultaneously with publication. A new acceptance at E4 does not erase the preceding result.

Finite observation convention: Each full-cycle row samples outputs before its represented rising edge, and the transition then computes the next row's state. Thus rows before E1, E2 and E3 see the retained ciphertext and zero done, and the row before E4 first sees the E3 result and asserted done. No physical clk level is present in this finite interface. This is an active-edge scenario in which sampled reset assertions are held through the represented edge; the output observation includes the settled asynchronous reset effect. It does not simulate assertion followed by release entirely between sampled edges and does not limit the circuit's obligations for such pulses. No step_ns or sample_offset_ns is specified by the supplied interface; row numbers are edge-scenario indices and do not establish a nanosecond period or delay.

5. Behaviour
Declaration facts confirmed by Q10: clk, reset and start are one-bit input wire ports; plaintext is input wire [14:0]; key is input wire [44:0]; ciphertext is output reg [14:0]; done is a one-bit output reg port.
The module spelling is hill_cipher; the normative declaration order is clk, reset, start, plaintext, key, ciphertext, done, as confirmed by Q10. There are no declared parameters or symbolic port ranges, and no non-port verification bindings.

The retained original requirements, including their explicit local revision HB1–HB4, remain authoritative. HB1 already corrects the malformed formula and the example's letter labels, and HB2 already extends the physical operand encoding domain; these are source-supplied corrections, not new answer amendments. No further source amendment is made here.

With reset low, start is sampled as a level only on an idle rising edge: high captures a job and low accepts nothing. All busy edges E1 through E3 ignore start, with no queue, restart, interruption, or cancellation. Lowering start after acceptance does not cancel the job. A pulse wholly between eligible rising edges has no effect. Continuously high start causes acceptances at E0, E4, E8 and so on absent reset. On an idle edge with start low, ciphertext holds and done clears. Reset aborts a job, and a still-high start may accept a fresh job on the first rising edge after release.

plaintext is captured in its entirety only at an idle rising edge with reset low and start high; subsequent changes do not affect that job. key is captured in its entirety at that same acceptance edge; subsequent changes do not affect that job. Changes to either operand while idle with start low or while reset is high have no output effect. Changes at E4 affect a new job only if it is accepted there. After reset cancellation, a fresh job uses the operands present at its fresh acceptance.

For i,j in 0..2, P_j is the unsigned five-bit field plaintext[14-5*j : 10-5*j], and K_ij is the unsigned five-bit field key[44-5*(3*i+j) : 40-5*(3*i+j)]. For captured operands, C_i = (K_i0*P_0 + K_i1*P_1 + K_i2*P_2) modulo 26, without truncating any product or sum. Products may reach 961 and the unsigned sum may reach 2883; arithmetic must retain that complete range before modulo 26. Only the final residue, in 0..25, is packed as a five-bit unsigned field ciphertext[14-5*i : 10-5*i]. All physical encodings 0..31 obey this numeric rule, including encodings 26..31. Matrix invertibility is not required for encryption. Alphabet labels use A=0 through Z=25. The first letter and first matrix entry occupy the most significant fields, and the matrix fields proceed in row-major order. The CAT numeric example yields [22,1,1], packed as 15'h5821 and labeled WBB under HB1.

ciphertext publishes only at the third rising edge after acceptance and otherwise retains its preceding value, except for asynchronous reset. done clears at every reset-low rising edge except a completion edge, where it asserts for the following interval. Busy requests and external operand changes cannot delay, accelerate, or cancel completion. Every aborted job is suppressed permanently; a fresh job after reset has its own complete three-interval schedule.
