<!-- original-requirements:start -->
Based on the requirements below, design a performance counter module that counts events triggered by a CPU and has a software-controlled reset.

**Requirements**:
- The counter will increment when a trigger event from the CPU pipeline (`cpu_trig_i`) is received.
- The counter's value should only be readable via a software request (`sw_req_i`). If there is no read request, the output should remain zero.
- Once the software reads the value, the counter resets to zero in the next cycle.
- The counter and the software read are independent and have no protocol dependencies.
- The counter width should be parameterizable.
- Use positive edge-triggered flip-flops with an asynchronous reset.

**Interface Definition**:
- `clk`: Clock signal (input).
- `reset`: Active-high reset signal (input).
- `sw_req_i`: Software request signal (input).
- `cpu_trig_i`: CPU trigger signal (input).
- `p_count_o [CNT_W-1:0]`: Performance counter output (output).

**Behavior**:
- On reset, the counter value is set to zero.
- The counter starts incrementing when `cpu_trig_i` is active, but the value is only output on `p_count_o` when a software read (`sw_req_i`) occurs.
- After the software reads the counter, it resets to zero on the next cycle.

**Boundary Conditions:**
- The counter should handle overflow correctly based on its parameterized width (`CNT_W`).

Provide a parameterizable Verilog module that meets these requirements. Ensure all timing and synchronization aspects, such as clock and reset behavior, are clearly handled.

1. Module and ports



3. Reset

`reset` is active high and asynchronous. Assertion is an effective event independent of `clk` and has priority over every simultaneous input. Immediately after assertion, `count_q` and `p_count_o` are zero and post-reset counting is disabled. They remain so while reset is asserted. Release alone changes no state or output.

Before reset has ever been asserted and before any rising edge has established `p_count_o`, `p_count_o` is hardware-unknown. This unknown is expressly established by Q1 and Q4--Q8 and is limited to state not yet established by an effective event. Before reset, a rising edge with `sw_req_i` high establishes `p_count_o` as zero-extended `cpu_trig_i`; without a request, increment or hold preserves an unknown prior value. The finite model's invalid initial registers represent only this disclosed pre-event state and do not create any wider hardware power-up guarantee.

After reset release, counting remains disabled. On each rising edge while disabled, high `cpu_trig_i` retains zero and remains disabled. The first rising edge sampling low `cpu_trig_i` retains zero and enables the answered `p_count_o` behavior beginning at the following rising edge; `sw_req_i` is ignored on that enabling edge. A later reset assertion immediately restarts this sequence.

4. Timing

Ordinary sampling and state updates occur only on the positive edge of `clk`; static levels and falling edges have no effect. Asynchronous reset assertion is the sole exception. `p_count_o` is a registered `CNT_W`-bit output. There is no completion pulse or serialized output.

For any positive edge Ek, pre-edge state and operands determine post-edge registered values. An enabled request at Ek publishes zero-extended `cpu_trig_i` immediately after Ek. An enabled trigger without a request publishes `(pre-edge p_count_o + 1) mod 2**CNT_W` immediately after Ek. Mode advancement is simultaneous: an edge that changes disabled to enabled still publishes zero, and enabled behavior starts at the next edge.

For the source counter-clear timing, E0 is the positive edge accepting `sw_req_i`. The request schedules the counter reset for E1, the next positive edge after one completed clock interval. At E1 the pre-edge pending clear supplies a zero base, and a trigger accepted at E1 independently contributes one, so post-edge `count_q` is zero when `cpu_trig_i` is low and one when it is high. This preserves both the next-cycle clear and the stated independence of triggering and software reading.

The finite model has no physical `clk` input: each full-cycle step denotes one positive edge. Row k observes settled `out(s[k], i[k])` before that edge, and the transition is first visible in row k+1. The scenarios include reset held asserted at sampled edges; they do not restrict legal asynchronous reset pulses between edges. No numerical `timing.step_ns` or `timing.sample_offset_ns` is present in the interface, so row numbers are active-edge indices, not implicit 10 ns ticks. This observation convention is separate from the unspecified physical clock period and reset propagation delay.

5. Behaviour

All arithmetic is unsigned at `CNT_W`. Addition is evaluated from the pre-edge `CNT_W`-bit operand, and the stored result is truncated at the `CNT_W` register boundary; therefore all ones increments to zero. The concrete finite instance binds `CNT_W=8`, while the public module remains parameterized.

The source-named `count_q` is distinct from the public `p_count_o`. Reset establishes `count_q=0`. Subject to reset priority, every positive edge with `cpu_trig_i=1` contributes one modulo `2**CNT_W`. A request accepted at E0 schedules the zero base at E1 as specified in the timing section. With neither a pending clear nor a trigger, `count_q` retains its prior value. The source-supplied `count_q` waveform remains a normative illustration of this distinct counter state.

Before the first reset assertion, each positive edge applies this `p_count_o` priority: high `sw_req_i` replaces it with the `CNT_W`-bit zero-extension of `cpu_trig_i`; otherwise high `cpu_trig_i` increments its current value modulo `2**CNT_W`; otherwise it holds. An increment or hold cannot make an initially unknown value known.

After reset has established the disabled condition, reset has highest priority. While disabled, high `cpu_trig_i` at a positive edge holds zero and remains disabled; low `cpu_trig_i` holds zero and enables normal behavior only for later edges, regardless of `sw_req_i`. Once enabled, each positive edge independently applies this priority: high `sw_req_i` replaces `p_count_o` with zero-extended `cpu_trig_i`; otherwise high `cpu_trig_i` increments it modulo `2**CNT_W`; otherwise it retains its value. Repeated requests repeat the replacement. Changes between positive edges have no effect except asynchronous reset assertion.

Verification-visible `clk` advances ordinary state only on positive edges; static levels and falling edges do not advance it. It has no terminal behavior and continues indefinitely.

Verification-visible `reset` asynchronously clears both specified values and disables answered output behavior; assertion is the advance guard, continued assertion retains reset state, and release alone does nothing. It has no terminal behavior.

Verification-visible `sw_req_i` is sampled on positive edges under the phase-specific priorities above and schedules the source counter clear. It is ignored for `p_count_o` during reset and during disabled/enabling phases. It has no terminal behavior.

Verification-visible `cpu_trig_i` is sampled on positive edges and separately governs `count_q`, output-mode enabling, output replacement data, or output increment as stated. Reset overrides it. It has no terminal behavior.

Verification-visible `p_count_o` changes on asynchronous reset assertion or immediately after qualifying positive edges and otherwise retains its registered value. Observation continues indefinitely; there is no terminal behavior.
