<!-- original-requirements:start -->
Design a System Verilog module named `wishbone_to_ahb_bridge`. The module facilitates communication between a Wishbone master and an AHB slave, translating Wishbone protocol signals into corresponding AHB protocol signals. The bridge supports single transfers and provides configurable data width for byte, halfword, and word-level transactions.

## Specifications

### Inputs
- **Wishbone Ports (from WB Master):**
  - `clk_i`: Clock signal for Wishbone operations.
  - `rst_i`: Active-low reset signal to initialize the bridge.
  - `cyc_i`: Indicates a valid Wishbone transaction cycle.
  - `stb_i`: Strobe signal for valid data on the Wishbone interface.
  - `sel_i[3:0]`: Byte enables to select which bytes are active.
  - `we_i`: Write enable signal.
  - `addr_i[31:0]`: Address for the Wishbone transaction.
  - `data_i[31:0]`: Write data from the Wishbone master.
- **AHB Ports (from AHB Slave):**
  - `hclk`: Clock signal for AHB operations.
  - `hreset_n`: Active-low reset signal for the AHB interface.
  - `hrdata[31:0]`: Read data from the AHB slave.
  - `hresp[1:0]`: AHB response signal.
  - `hready`: Indicates when the AHB slave is ready.

### Outputs
- **Wishbone Outputs:**
  - `data_o[31:0]`: Read data back to the Wishbone master.
  - `ack_o`: Acknowledge signal for Wishbone operations.
- **AHB Outputs:**
  - `htrans[1:0]`: AHB transaction type.
  - `hsize[2:0]`: Size of the AHB transfer.
  - `hburst[2:0]`: Burst type (always single in this design).
  - `hwrite`: Write enable signal for AHB transactions.
  - `haddr[31:0]`: Address for the AHB transaction.
  - `hwdata[31:0]`: Write data to the AHB slave.

## Functional Requirements
1. **Protocol Translation**:
   - Translate Wishbone protocol signals to AHB-compliant signals.
   - Support byte, halfword, and word-level transactions based on `sel_i`.

2. **Address Fixing**:
   - Derive AHB-compliant addresses from Wishbone addresses using `sel_i`.

3. **Single Transfer Support**:
   - Only SINGLE AHB transfers (`hburst = 3'b000`) are supported.

4. **Data Handling**:
   - Perform endian conversion for read and write data between Wishbone and AHB.

5. **Control Signals**:
   - Use an FSM-like approach to manage transaction phases (`htrans`), including IDLE, NON-SEQUENTIAL, and BUSY states.

6. **Pipeline Management**:
   - Handle data and address phases for AHB transactions with proper synchronization using `hready`.

## Implementation Details
- **Endian Conversion**:
  - Convert between Wishbone's little-endian format and AHB's data handling.
  - Use `sel_i` to determine active bytes in a transfer.

- **Signal Holding**:
  - To ensure proper synchronization, hold transaction attributes (address, size, transaction type, etc.) during AHB operations.

- **Reset Behavior**:
  - Ensure all internal registers are reset to default values when `rst_i` or `hreset_n` is asserted.

- **Latency**:
  - Ensure proper acknowledgment (`ack_o`) to the Wishbone master only after completing the AHB transaction (`hready` is asserted).


## Edge Cases
1. **Invalid Byte Selection**:
   - Handle invalid or conflicting `sel_i` values gracefully without causing data corruption.

2. **AHB Slave Busy**:
   - Test the behavior when the AHB slave asserts `hready` late, stalling the transaction.

3. **Back-to-Back Transactions**:
   - Ensure correct operation when Wishbone initiates a new transaction immediately after the previous one completes.

1. Module and ports.



3. Reset.

Both rst_i and hreset_n are active-low asynchronous resets. Assertion of either immediately cancels a pending request, clears ack_o to 0, and clears the retained read result to 32'h00000000. Assertion has priority over a simultaneous rising hclk edge. Reset does not gate the combinational outputs: htrans, hsize, hburst, hwrite, haddr, and hwdata continue to obey their current-input laws. While reset is asserted, data_o equals current hrdata during cyc_i && stb_i && !we_i and equals 32'h00000000 otherwise.

Reset release alone changes no state and produces no pulse. On the first rising hclk edge after release, a live request is accepted if none is pending, and ack_o remains low. Without a live request, the reset-established state remains: no request pending, ack_o low, and retained read data zero. Edge history follows hclk while reset is asserted, so release while hclk is already high does not manufacture a rising edge.

Implementation choice C1 — pre-reset initialization. Before any reset assertion has been observed, the concrete implementation represented by the verification model starts with no pending request, ack_o low, retained read data 32'h00000000, and hclk treated as previously low. Thus an initially high hclk is its first rising edge. This is a compatible implementation decision only in the otherwise unconstrained pre-reset power-up scope; it is not a fact established by the source, not a hardware power-up guarantee imposed on other compatible implementations, and not a reset-before-use restriction. All combinational laws apply immediately, and reset or ordinary hclk events establish the specified subsequent behavior.

4. Timing.

Only rising hclk edges advance transaction state. clk_i has no effect at either level or edge, and no relationship between clk_i and hclk is required. Pausing hclk pauses state progress; pausing or changing clk_i does not.

Define E0 as a rising hclk edge at which no request is pending and cyc_i && stb_i is true immediately before the edge. E0 accepts the request; ack_o remains low after E0. Each subsequent rising hclk edge ends one completed hclk interval after the preceding edge. At every such edge while pending, pre-edge hready=0 retains the pending request and ack_o low. Let Ec be the first rising edge later than E0 with pre-edge hready=1. The transfer completes at Ec; pre-Ec we_i selects read versus write, and for a read pre-Ec hrdata is retained. ack_o becomes high after Ec for exactly one completed hclk interval. At the next rising edge, ack_o clears and that same edge may accept a held or newly asserted request; Ec itself does not accept another request. Deasserting cyc_i or stb_i after E0 does not cancel the pending request.

From reset assertion through release and the first three rising edges: reset assertion immediately cancels pending state and clears registered results; release alone does nothing; the first eligible rising edge E0 accepts but does not acknowledge; the second rising edge either waits if hready is low or completes if hready is high; the third rising edge either continues waiting, completes a still-pending request, or clears the one-interval ack_o pulse and may accept another request. These actions use pre-edge inputs and state; counter or index advancement is not applicable because the design has none.

The evaluated half-cycle rows are settled observations before the pending transition. A row presenting a low-to-high hclk change therefore shows pre-edge registered values; the resulting state appears in the next row. Row k uses the interface's half-cycle observation cadence. This observation convention is separate from circuit timing: the source specifies no physical clock period or propagation delay, and there is no implicit 10 ns clock tick.

Per output: data_o is zero-latency combinational hrdata during a live read and otherwise is the registered retained read result; ack_o is registered with the E0/Ec latency above and is a one-completed-hclk-interval pulse; htrans, hsize, hburst, hwrite, haddr, and hwdata are zero-latency combinational outputs. No output is periodic.

Amendment A5. The exact original clause "- Use an FSM-like approach to manage transaction phases (`htrans`), including IDLE, NON-SEQUENTIAL, and BUSY states." is superseded only for observable htrans encoding by Q9, whose certain answer law is exactly: "htrans is the live request encoding 2'b10 whenever cyc_i && stb_i and is 2'b00 otherwise, independent of acceptance, waiting, completion, and reset state." BUSY is not emitted; pending/wait/completion behavior remains.

A live request is cyc_i && stb_i. It drives htrans=2'b10; otherwise htrans=2'b00. A rising hclk edge samples a live request only when none is pending. Deasserting either request input does not cancel a pending transfer. hready is ignored when none is pending; while pending, hready=0 at a rising edge waits and hready=1 completes. A held request may be accepted again only at a rising edge after its completion edge. clk_i has no effect. Every hresp value 2'b00 through 2'b11 has no effect on outputs, waiting, completion, read/write selection, retries, or repetition.

hburst is continuously 3'b000. hwrite is current we_i. hwdata is current data_i bit-for-bit. hsize is 3'b000 for sel_i 0001, 0010, 0100, or 1000; 3'b001 for 0011 or 1100; and 3'b010 for every other pattern, including 0000, every noncontiguous mask, and 1111. haddr preserves addr_i[31:2] and replaces bits [1:0] with 00 for 0001 or 0011, 01 for 0010, 10 for 0100 or 1100, and 11 for 1000; for every other sel_i value haddr equals addr_i completely. All 16 sel_i patterns are deterministic, none suppresses a live request, and all follow the normal acknowledgement and data laws. addr_i, data_i, sel_i, and we_i changes take effect immediately during reset, idle, waiting, completion, and repeated transactions.

During cyc_i && stb_i && !we_i, data_o equals current hrdata bit-for-bit, including during reset. Otherwise data_o equals the last hrdata retained at a rising hclk completion edge whose pre-edge we_i was zero; after reset that retained value is zero. A write completion leaves it unchanged. Outside a live read, hrdata changes have no effect. The retained value survives idle, wait edges, writes, and restarts until another completed read or either reset.
