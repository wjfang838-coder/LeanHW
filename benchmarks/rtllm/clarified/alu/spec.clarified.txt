Please act as a professional verilog designer.

Implement an ALU for a 32-bit MIPS-ISA CPU. The “a” and “b” are the two operands of the ALU, the “aluc” is the opcode, and the “r” gives out the result. “zero” means if the result is zero, “carry” means if there is a carry bit, “negative” means if the result is negative, “overflow” means if the computation is overflow, the “flag” is the result of “slt” and “sltu” instructions. The supported operations and corresponding opcode are shown below:
    parameter ADD = 6'b100000;
    parameter ADDU = 6'b100001;
    parameter SUB = 6'b100010;
    parameter SUBU = 6'b100011;
    parameter AND = 6'b100100;
    parameter OR = 6'b100101;
    parameter XOR = 6'b100110;
    parameter NOR = 6'b100111;
    parameter SLT = 6'b101010;
    parameter SLTU = 6'b101011;
    parameter SLL = 6'b000000;
    parameter SRL = 6'b000010;
    parameter SRA = 6'b000011;
    parameter SLLV = 6'b000100;
    parameter SRLV = 6'b000110;
    parameter SRAV = 6'b000111;
    parameter LUI = 6'b001111;

Module name:  
    alu               
Input ports:
    a: a 32-bit input operand
    b: a 32-bit input operand
    aluc: a 6-bit control signal for selecting the operation to be performed
Output ports:
    r: a 32-bit output representing the result of the operation
    zero: a 1-bit output indicating whether the result is zero
    carry: a 1-bit output indicating whether a carry occurred during the operation
    negative: a 1-bit output indicating whether the result is negative
    overflow: a 1-bit output indicating whether an overflow occurred during the operation
    flag: a 1-bit output representing a general flag, which is set based on specific operations (SLT and SLTU)

Implementation:
The module uses parameters to define the control signals for various operations, such as ADD, SUB, AND, OR, etc. 
The module assigns the input operands to the signed wires and the output result (r) to the lower 32 bits of the register (res[31:0]). The flag output is determined based on the control signal (aluc) and is set to '1' when the operation is SLT or SLTU, and 'z' (high-impedance) otherwise. The zero output is set to '1' when the result is all zeros, and '0' otherwise.
Inside the always block, a case statement is used to perform the appropriate operation based on the control signal (aluc). The result is assigned to the register (res) accordingly. For shift operations (SLL, SRL, SRA, SLLV, SRLV, SRAV), the shift amount is determined by the value of 'a' or 'a[4:0]'. For the LUI operation, the lower 16 bits a[15:0] are concatenated with 16 zeros to form the result r={a[15:0],16'b0}. This explicit local benchmark correction agrees with its native oracle.
If the control signal (aluc) does not match any defined operation, the result is assigned as 'z' (high-impedance).

3. Reset
There is no reset or clock port and no reset assertion, release, reset edge, or reset-dependent state. No reset-defined initial value is promised for r, zero or flag before initial operand/control evaluation; their pre-evaluation power-up values are unconstrained by the requirements. This does not require hardware X or delay normal evaluation. carry, negative and overflow are z even before the first input change. After initial evaluation and settling, every output obeys the laws below, including at trace row zero. The finite model has no stored hardware data; its Unit initial state promises no power-up data value. No initialization implementation choice is required.

4. Timing
r and zero are combinational outputs with zero clock-cycle latency: each a, b or aluc change recomputes them at the same simulation time after the deferred result update and subsequent delta-cycle settling. flag is combinational with zero clock-cycle latency and follows the comparison after continuous-expression delta-cycle settling. carry, negative and overflow remain continuously z, independently of all input events. There are no completion pulses, periodic outputs, bounded transactions, acceptance edges or restart edges.

Stable inputs preserve settled values; simultaneous changes use the resulting input tuple, and repeated changes recompute without a transaction hold interval. A pre-edge observation sees the settled output for inputs already present before an external edge. A change on that external edge produces the new settled output at the same time; no subsequent E1 edge is required. No external edge advances hardware state. There is no enable or inactive control level: every aluc value selects an operation or the unmatched branch. No output retention from a previous opcode is permitted after a new tuple settles.

Observation convention, separately from circuit timing: the finite fullCycle model samples out before its inert step, for fully known 32-bit operands and a 6-bit control with default public opcode parameters. Each row is an independently settled current-input observation, including row zero. This interface supplies neither timing.step_ns nor timing.sample_offset_ns; no numerical sampling interval, 10 ns clock tick, physical period or propagation delay is inferred. Where an external observation schedule supplies step_ns, row k denotes k * step_ns after settling, subject to that schedule's sample_offset_ns. The model covers settled tuples rather than delta-cycle transients or pre-evaluation power-up observations.

5. Behaviour
The retained original prose remains authoritative except for the individually scoped amendments below. These are amendments, not preservation claims. All exact old excerpts in the notices are superseded-source quotations only. Public opcode parameters retain the declarations rendered in section 1; the finite trace uses their default values. JR is public but introduces no additional supported operation: its default value selects the unmatched branch. The operation laws refer to the corresponding public opcode parameters; parameter overrides do not change port widths or the arithmetic laws. No new parameter-domain restriction is introduced.

For fully known operands, ADD and ADDU give the low 32 bits of a+b; SUB and SUBU give the low 32 bits of a-b. Signed ADD and SUB operate on two's-complement operands sign-extended to a 33-bit expression context; unsigned ADDU and SUBU operate on zero-extended operands in that context. Arithmetic wraps modulo 2^33 before the low 32-bit r projection. AND gives a & b; OR gives a | b; XOR gives a ^ b; NOR gives the low 32 bits of ~(a | b). The bitwise operands are zero-extended in the 33-bit result context, so NOR's extra result bit is 1. No saturation is specified.

SLT gives r=1 exactly when signed two's-complement a is less than signed b, otherwise r=0; SLTU gives r=1 exactly when unsigned a is less than unsigned b, otherwise r=0. These are 32-bit results. For SLT, flag is 1 iff signed two's-complement a < signed b; for SLTU, flag is 1 iff unsigned a < unsigned b. It is 0 for the corresponding false comparison and z for every other opcode.

SLL, SRL and SRA use the full 32-bit bit pattern of a as an unsigned shift count. SLLV, SRLV and SRAV use a[4:0], ignoring a[31:5]. SLL and SLLV shift b left; SRL and SRLV shift b right with zero fill; SRA and SRAV shift signed b right with b[31] fill. The expression context is 33 bits; r is projected to its low 32 bits only after shifting. Counts >=32 give r=0 for left and logical right shifts, and 32 copies of b[31] for arithmetic right shifts. Do not truncate a left shift to 32 bits before computing zero. A count with a[31]=1 remains an unsigned count, including for SRA. These choices resolve the original full-a versus a[4:0] ambiguity through certain question Q21, scope source@50de02abe6034355; they do not amend another operation.

LUI gives r={a[15:0],16'b0} and ignores b. This preserves the original explicit local correction. Any opcode not matching a supported operation gives high impedance on all 32 bits of r, zero=x, flag=z, carry=z, negative=z and overflow=z. The x on zero is a hardware-unknown equality result explicitly authorized by Q8, restricted to the unmatched branch; it is not epistemic uncertainty or an arbitrary value choice.

For fully known operands, zero tests the complete 33-bit expression value, not merely the low 32-bit r. For ADD, zero=1 exactly when the sum of sign-extended operands modulo 2^33 is zero; for ADDU it tests the zero-extended sum modulo 2^33. For SUB and SUBU, zero=1 exactly when a=b. For AND, OR and XOR, zero=1 exactly when their 32-bit bitwise result is zero. NOR always gives zero=0, including when a|b=32'hffffffff. For SLT and SLTU, zero=1 exactly when the corresponding signed or unsigned comparison is false. For SLL and SLLV with the corresponding count n, zero=1 exactly when (unsigned b * 2^n) modulo 2^33 is zero: n=32 tests b[0]=0 and n>=33 always gives zero=1. For SRL and SRLV, zero=1 exactly when the logical right-shift result is zero. For SRA and SRAV, zero=1 exactly when sign-extended 33-bit two's-complement b shifted arithmetically by the corresponding unsigned count is zero. For LUI, zero=1 exactly when a[15:0]=0. Otherwise zero=0 in these known-operand supported-operation branches.

b is ignored for LUI and unmatched opcodes; every other operation uses it according to its law. a supplies arithmetic, logical or comparison data, the applicable shift count, or the LUI low half. Operand changes have no effect on the constant z status outputs; aluc selects the current operation for every value. There is no disabled mode, pending computation, cancellation, warm-up interval or omitted repeated request.

carry=z continuously for every operand and opcode, including before the first input change. negative=z continuously for every operand and opcode, including before the first input change. overflow=z continuously for every operand and opcode, including before the first input change. No input event or external sampling edge captures, clears, initializes or completes these outputs.
