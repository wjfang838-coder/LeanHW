01 / Overview

Making AI-generated hardware trustworthy

Language models can generate RTL from natural-language specifications. Reliable hardware development also requires an explicit interpretation of the intended behavior and evidence that the implementation satisfies it.

CHALLENGE 01

Ambiguous requirements

Natural-language descriptions may permit several distinct behaviors. A plausible RTL implementation can still disagree with what the designer intended.

CHALLENGE 02

Functional correctness

Passing a finite set of simulations does not establish correctness for all relevant states or execution lengths.

OUR APPROACH

Executable intent + proof

LeanHW clarifies requirements using discriminating traces, then uses Lean to prove that generated RTL refines the decided executable model.

Motivation

Two questions across hardware development

What behavior should the design implement? LeanHW formalizes candidate interpretations and asks the designer targeted questions when the interpretations disagree.

Does the generated implementation satisfy that behavior? LeanHW translates RTL into a Lean model and establishes a refinement relation through formal proof.

Interactive workflow

Follow the full process from ambiguous intent to clarified specifications, direct RTL generation, and machine-checked refinement.

A two-stage, proof-driven workflow

02 / Case Study

A complete RISC-V CPU

An end-to-end application of the LeanHW methodology to processor-level functional correctness: expressing instruction-set behavior as an executable reference, connecting a generated RTL CPU to that reference, and proving an unbounded refinement statement.

Case study summary

This case study illustrates what it means to verify a CPU beyond testing a collection of instructions. The intended behavior is described at the instruction-set level, while the hardware implementation evolves cycle by cycle. A proof connects these two different views of execution.

At the high level, the reference model specifies the architectural effects of an instruction: the program counter, general-purpose registers, and memory state. At the low level, the generated RTL describes the processor's control logic, datapath, and state updates. LeanHW establishes a relation between corresponding states and proves that RTL execution preserves the intended ISA behavior.

Central proof claim. Under the modeled instruction subset, environment assumptions, and observation relation, the generated RTL refines the executable RISC-V ISA specification. The exact supported instructions and assumptions must be checked against the proof artifacts before this statement is used as a broader ISA-compliance claim.

1. Verification goal

The specification and the implementation operate at different abstraction levels. The ISA model takes architectural steps; the RTL model takes clock cycles. A refinement proof must account for this difference and relate observable architectural state, rather than comparing internal signals one by one.

2. Executable ISA reference semantics

The reference model captures the architecturally visible behavior of the supported RISC-V instructions. An architectural state can include the program counter, register file, and memory. Executing an instruction updates this state according to the chosen instruction-set semantics.

-- Schematic Lean-style interface; illustrative, not repository source. structure ArchState where pc : Word regs : RegFile mem : Memory def isaStep (s : ArchState) : ArchState := execute (decode (fetch s.mem s.pc)) s

Formalizing this model makes ambiguities explicit, such as update timing, reset behavior, supported instruction variants, and memory assumptions. The decided executable model is the target for implementation verification.

3. RTL transition system

The generated Verilog is mapped to a Lean-level RTL representation through a deterministic translation step. Its semantics model concrete hardware state and clock-to-clock transitions. This makes it possible to reason about the actual RTL implementation within the proof environment.

-- Schematic relation; names are placeholders. rtlInit : RTLState → Prop rtlStep : RTLState → RTLState → Prop isaStep : ArchState → ArchState observe : RTLState → ArchState

The formalization boundary matters: the proof is about the semantics assigned to the translated RTL. The parser, translation coverage, and any environmental assumptions are part of the verification trusted base or its stated scope.

4. Cross-abstraction refinement

A refinement relation connects an ISA state to a concrete RTL state. It may relate the architectural registers, PC, and memory to internal RTL registers and datapath state. When one ISA instruction requires multiple RTL cycles, the proof must allow the corresponding sequence of concrete transitions.

Proving this relation requires establishing compatible initial states and showing preservation after each relevant transition or instruction boundary. The exact stuttering or step-matching formulation depends on the CPU implementation.

5. Proof decomposition and reuse

The verification task can be decomposed around instruction semantics, datapath operations, and invariant preservation. Useful intermediate facts include arithmetic or bit-vector properties, register-file read/write behavior, decoding conditions, and control-state invariants. Reusable lemmas reduce repeated proof effort across instructions and related modules.

6. Scope and assumptions

Processor verification claims should identify the supported ISA subset, reset behavior, memory interface, input constraints, treatment of illegal instructions, and any unmodeled behavior. These define the meaning of the refinement theorem. A complete CPU implementation does not automatically imply coverage of every RISC-V extension or microarchitectural feature.

For anonymous publication, keep the main theorem statement and its explicit assumptions alongside the code. This section intentionally avoids inventing a supported ISA subset or theorem identifier that cannot be confirmed from the current source files.

7. Reproducing the case study

The source package contains the CPU model, imported RTL semantics, refinement proofs, and replay scripts under case_cpu/. The memory CPU package includes a 999-line Verilog implementation, 38 supported instructions, native RAM, transaction-level ISA semantics, cycle-level LeanSpec, imported LeanRTL, and two-level refinement proofs. See the repository's README for proof scope and prerequisites.

case_cpu/ memory/ # CPU implementation, models, proofs and replay scripts lean/ # Base CPU and proof dependencies bridge/ # Shared bridging proof dependencies

Reproduce from the repository root with python3 case_cpu/memory/scripts/replay.py. The repository notes that historical validation records are not a fresh replay of every proof.
